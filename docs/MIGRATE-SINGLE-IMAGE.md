# Moving from the three-image layout to the single `tix` image

Deutsch: [MIGRATE-SINGLE-IMAGE.de.md](MIGRATE-SINGLE-IMAGE.de.md)

Releases up to `1.0.0-alpha.27` ran as `tix-web`, `tix-worker` and `tix-realtime` plus a bundled
Caddy proxy and a MinIO file store. From the next release on TIX ships **one image**,
`ghcr.io/renthner/tix`, which runs the shop, the realtime gateway and the worker in one container and
speaks plain HTTP on port 8080. The new compose file has three services only (`tix`, `postgres`,
`redis`).

**Your data stays where it is.** This guide keeps your PostgreSQL, Redis and MinIO volumes and runs
the new image in **S3 mode** against the MinIO you already have. Nothing is copied, nothing is
converted. Staying in S3 mode is fully supported for good; you can switch to the new
file-system storage later (last section) but you never have to.

> The new `docker-compose.yml` refuses to start with your old `.env`, and the new `tix-update.sh`
> refuses to replace an old compose file: nothing is changed by accident. Your **old** copy of
> `tix-update.sh` cannot know this, but it stops as well ("nothing was changed") because the new
> compose file does not validate with the old `.env`. Until you have followed this guide, do not
> update.

## What changes

| Before                                                           | After                                                                                       |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `tix-web`, `tix-worker`, `tix-realtime`                          | one `tix` container (`docker compose logs tix`)                                             |
| `migrate` one-shot service                                       | runs inside the `tix` start (migrations, seed, pre-update backup)                           |
| `docker compose run --rm migrate node dist/create-admin.mjs ...` | `docker compose run --rm tix create-admin --email ... --name ...`                           |
| Caddy (`proxy`) terminates TLS                                   | your own reverse proxy terminates TLS (or keep Caddy, see step 5)                           |
| `TIX_CHANNEL`, `PUBLIC_URL` in `.env`                            | `TIX_VERSION`, `APP_URL` in `.env`                                                          |
| Redis with password                                              | Redis on the internal network without password (the old `REDIS_PASSWORD` is no longer used) |
| MinIO credentials generated by `storage-credentials`             | the same files in the same volume, read by `tix` (`S3_*_FILE`)                              |
| `SESSION_SECRET` in `.env`                                       | unchanged (keep it, otherwise everybody is signed out)                                      |

## Before you start

1. **Back up.** Admin -> Backups: create a full backup and download it. Keep your `.env`
   (`cp .env .env.three-image.bak`) and a copy of `APP_ENCRYPTION_KEYS` outside the server. Keep
   `docker-compose.yml` as `docker-compose.three-image.yml.bak`.
2. Docker Compose 2.23.1 or newer (`docker compose version`).
3. Plan a short downtime (a few minutes). **Never run `docker compose down -v`** in this process: `-v`
   deletes the volumes that hold your data.

## Step 1 - stop the old stack

```bash
cd /path/to/your/tix        # the folder with docker-compose.yml and .env
docker compose down         # without -v!
docker volume ls | grep tix # postgres-data, redis-data, minio-data, storage-credentials ... must still be listed
```

The volume names carry your compose project name as a prefix (`COMPOSE_PROJECT_NAME`, default `tix`:
`tix_postgres-data` ...). The new files use the same names, so the volumes are picked up again.

## Step 2 - the new compose file

```bash
mv docker-compose.yml docker-compose.three-image.yml.bak
curl -LO https://github.com/Renthner/tix-platform/releases/latest/download/docker-compose.yml
```

(`releases/latest` points at the newest **stable** release; while only pre-releases exist, use
`releases/download/v<version>/docker-compose.yml` with the version from the release page.)

## Step 3 - edit `.env`

Keep everything you have (especially `POSTGRES_PASSWORD`, `APP_ENCRYPTION_KEYS`, `SESSION_SECRET`,
and `POSTGRES_USER` / `POSTGRES_DB` if you changed them). Add or change:

```ini
APP_URL=https://tickets.example.org   # the value of your old PUBLIC_URL
TIX_VERSION=stable                    # the value of your old TIX_CHANNEL (stable, next, 1, 1.0 or exact)
HTTP_PORT=8080                        # see below
TRUSTED_PROXIES=                      # see below
```

`TIX_CHANNEL`, `PUBLIC_URL`, `SITE_ADDRESS`, `HTTPS_PORT` and `REDIS_PASSWORD` are no longer read; you
can delete them later (the `.env` is passed to the container as it is, unused lines are harmless).

`HTTP_PORT` and `TRUSTED_PROXIES` depend on how your shop was reached:

- **Another reverse proxy in front of the bundled Caddy** (your `.env` had `SITE_ADDRESS=:80` and a
  `TRUSTED_PROXIES`): keep `HTTP_PORT` and `TRUSTED_PROXIES` exactly as they are. Your proxy keeps
  forwarding to the same port, now answered by `tix` directly. Skip step 5.
- **Caddy was the public entry with a domain** (`SITE_ADDRESS=tickets.example.org`, ports 80/443):
  either put your own TLS proxy in front (as above) or keep Caddy, see step 5. For the latter set
  `HTTP_PORT=127.0.0.1:8081` (so `tix` is only reachable from the server itself) and
  `TRUSTED_PROXIES=private_ranges`.
- **Plain HTTP test setup** (`SITE_ADDRESS=:80`): keep `HTTP_PORT`, leave `TRUSTED_PROXIES` empty. If
  `APP_URL` names a host (not `localhost`) but you open the shop by another name or by `IP:8080`, `tix` answers
  421: add that name to `TIX_ALLOWED_HOSTS` (or `*`).

With an `https://` `APP_URL` prefer the **exact IP/CIDR** of your proxy for `TRUSTED_PROXIES` over
`private_ranges` (TIX warns about the latter), and publish the port only on the proxy's interface.
Requests from a trusted proxy are never rejected by the host check, so `TIX_ALLOWED_HOSTS` is only needed
for direct access ([details](INSTALL.md#built-in-proxy-host-check-and-limits)).

$1
**Delete the lines `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD` from `.env`** if your old file has them
(installations from before the credentials were generated). The whole `.env` is passed to the `tix`
container, and it must never see the MinIO administrator pair; MinIO itself reads it from the
`storage-credentials` volume (step 4), so removing the lines is safe.

## Step 4 - the override file

**Do you already have a `docker-compose.override.yml`?** Then do not simply replace it. The old services are
gone, and an override that still configures `proxy`, `web`, `worker`, `realtime` or `migrate` makes
`docker compose config` fail (a service without an image). Convert it first:

- Everything under `proxy:` (Traefik labels, `networks`, `ports: !reset []`, published ports) moves to
  `tix:`. In Traefik labels change `loadbalancer.server.port` from `80` to `8080`.
- Delete the sections of `web`, `worker`, `realtime`, `migrate`, `minio-init` and `storage-credentials`
  (memory limits and similar settings do not exist in the new compose file; add what you still need under
  `tix:`).
- Then merge the blocks below into the same file: one file, one `services:` key, one `volumes:` key.

Create `docker-compose.override.yml` next to `docker-compose.yml`. Compose reads it automatically
and `tix-update.sh` never touches it, so later updates replace only `docker-compose.yml`.
It points `tix` at your existing MinIO and re-adds MinIO itself (the buckets, the application user
and its policy already exist inside the MinIO volume; the `storage-credentials` and `minio-init`
helper services are not needed any more):

```yaml
services:
  tix:
    environment:
      STORAGE_DRIVER: s3
      S3_ENDPOINT: http://minio:9000
      S3_REGION: ${S3_REGION:-us-east-1}
      S3_ACCESS_KEY_ID_FILE: /run/tix-storage/s3-access-key-id
      S3_SECRET_ACCESS_KEY_FILE: /run/tix-storage/s3-secret-access-key
      S3_BUCKET_ASSETS: ${S3_BUCKET_ASSETS:-tix-assets}
      S3_BUCKET_DOCUMENTS: ${S3_BUCKET_DOCUMENTS:-tix-documents}
      S3_BUCKET_BACKUPS: ${S3_BUCKET_BACKUPS:-tix-backups}
      S3_FORCE_PATH_STYLE: 'true'
    volumes:
      - storage-credentials:/run/tix-storage:ro
    depends_on:
      minio:
        condition: service_healthy

  minio:
    image: ${MINIO_IMAGE:-pgsty/minio:RELEASE.2026-08-04T00-00-00Z}
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
    command: ['server', '/data', '--console-address', ':9001']
    environment:
      MINIO_ROOT_USER_FILE: /run/tix-storage/minio-root-user
      MINIO_ROOT_PASSWORD_FILE: /run/tix-storage/minio-root-password
    volumes:
      - minio-data:/data
      - storage-credentials:/run/tix-storage:ro
    healthcheck:
      test: ['CMD', 'curl', '-fsS', 'http://127.0.0.1:9000/minio/health/live']
      interval: 5s
      timeout: 3s
      retries: 20

volumes:
  minio-data:
  storage-credentials:
```

Notes:

- The `storage-credentials` volume holds four files created by the old stack: the MinIO root pair
  (`minio-root-user`, `minio-root-password`, readable by root only, used by `minio`) and the
  application pair (`s3-access-key-id`, `s3-secret-access-key`, owned by uid 1000, the `node` user
  of the image, so `tix` can read them). `tix` never sees the root pair.
- If you set `MINIO_IMAGE`, `S3_BUCKET_*` or `S3_REGION` in your old `.env`, those values are used
  because the override interpolates them.
- Installations created before the credentials were generated may have had `S3_ACCESS_KEY_ID` and
  `S3_SECRET_ACCESS_KEY` in `.env`: the old stack copied them into the volume once, so the files exist; the
  plain values in `.env` are passed to `tix` and are identical to the files. (`MINIO_ROOT_USER` /
  `MINIO_ROOT_PASSWORD` must be removed from `.env`, see step 3.)
- Redis: the override does **not** carry the password over. Redis is only reachable inside the
  Docker network. Your `redis-data` volume (the Redis AOF) is used unchanged; the password was a
  server setting, not part of the data. If you use an **external** Redis instead, set
  `REDIS_URL=redis://:password@host:6379/0` under `tix: environment:` (the bundled `redis` service is
  then unused).
- PostgreSQL: if you never changed `POSTGRES_USER` / `POSTGRES_DB` (both `tix`), nothing is needed.
  Otherwise add to the override: under `tix: environment:` `DB_USER` and `DB_NAME` with your values,
  and under `postgres:` `environment:` `POSTGRES_USER` / `POSTGRES_DB` plus
  `healthcheck: { test: ['CMD-SHELL', 'pg_isready -U <user> -d <db>'] }`. `POSTGRES_PASSWORD` is
  used as before.
- The old `pre-update-backups` volume is no longer mounted: the pre-update backup now goes to the
  `tix-backups` bucket. Files that are still inside the old volume stay there (list them with
  `docker run --rm -v tix_pre-update-backups:/b alpine ls -la /b`); delete the volume once you no
  longer need them.

## Step 5 - Caddy for HTTPS (only if Caddy was your public entry)

Skip this step when your own reverse proxy terminates TLS. Otherwise save this `Caddyfile` next to
the compose file:

```
{$SITE_ADDRESS} {
	encode zstd gzip
	reverse_proxy tix:8080
}
```

and add the service and its two volumes to `docker-compose.override.yml` (the certificates are in
the `caddy-data` volume of the old stack and are reused):

```yaml
services:
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
    environment:
      SITE_ADDRESS: ${SITE_ADDRESS:?set SITE_ADDRESS in .env}
    ports:
      - 80:80
      - 443:443
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
      - caddy-config:/config
    depends_on:
      tix:
        condition: service_healthy

volumes:
  caddy-data:
  caddy-config:
```

(Merge the `services:` and `volumes:` blocks with those of step 4: one file, one `services:` key.)
Keep `SITE_ADDRESS=tickets.example.org` in `.env`, set `HTTP_PORT=127.0.0.1:8081` and
`TRUSTED_PROXIES=private_ranges` as described in step 3.

## Step 6 - start

```bash
docker compose config -q                 # validates compose + .env + override, prints nothing when fine
docker compose pull
docker compose up -d --remove-orphans    # also removes the containers of the old web/worker/realtime/proxy services
docker compose logs -f tix               # migrations run first; Ctrl+C when the shop answers
```

Check: the shop and the admin open, images and documents load (they come from your MinIO), Admin ->
System shows the new version, and `docker compose ps` lists `tix`, `postgres`, `redis`, `minio`
(plus `caddy`). Then create an admin if you ever need one with
`docker compose run --rm tix create-admin --email you@example.org --name "Your Name"`.

If something is wrong, `docker compose down` and read the logs first. Going **back to the old layout** only
works if the new release has applied no database migration yet (check the CHANGELOG; a migration runs when
the `tix` container starts): then put `docker-compose.three-image.yml.bak` and `.env.three-image.bak` in place
and start the old stack with its old image tags. Otherwise the old images cannot read the newer schema:
install the old version fresh and restore a normal backup that was taken before the move (step 0 of
"Before you start"). A "Before update" backup is taken automatically before the first migration (Admin ->
Backups); it brings back your data on the **new** version, not the old one.

## Afterwards

- **Updates** work as before with `./tix-update.sh` (download the script of the new release once).
  It only replaces `docker-compose.yml`; your `.env` and the override stay.
- **Housekeeping** after a week without problems: `docker image prune` removes the old
  `tix-web` / `tix-worker` / `tix-realtime` images; `docker volume rm tix_pre-update-backups`
  once its files are not needed.
- **GitHub packages:** the old `tix-*` packages are no longer built; existing tags stay pullable.

## Optional: switch to the file-system storage later

The new default stores files in a plain directory on the `tix-data` volume instead of MinIO (see
[STORAGE.md](STORAGE.md)). There is no in-place converter and no need for one. If you want to drop
MinIO anyway:

1. Admin -> Backups: create a full backup (database + files) on the running S3-mode installation and
   download it.
2. Set up a second, empty installation with the standard compose file (no override, new volumes,
   a different `COMPOSE_PROJECT_NAME`, **the same `APP_ENCRYPTION_KEYS`**) on the same version.
3. In its admin upload the backup (Backups -> upload) and restore it. Database and files land in
   the new storage; verify the shop; then switch DNS / the proxy to it and retire the old stack.

Keep in mind that backups on the same volume as the files do not survive the loss of the disk:
configure an external backup target in Admin -> Backups.
